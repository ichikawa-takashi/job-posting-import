# 求人票PDF → 公開まで

「求人票追加しました」と言われたら、この手順で最後まで進める。
ユーザーがやることは、最後に `push.command` をダブルクリックして `y` を押すだけにする。

## 全体の流れ

0. **`json/_server.json` を読み、サーバーの現況（全員ぶん）を把握する**
   → 下記「複数人で使っている場合」を必ず参照
1. `pdf/` フォルダを `ls` して、**まだJSONになっていないPDF**を見つける
   （日本語の長いファイル名のまま残っているものが未処理。処理済みは `<id>.pdf` にリネームされている）
2. そのPDFを `Read` で読む（文字化けしていても画像として認識できる）
3. `WebSearch` で会社名＋職種を調べ、研修制度・実績・数字を補強する
4. 下記スキーマのJSONを `json/<id>.json` に書き出す
5. **`python3 tools/check-json.py` を実行し、✗ が消えるまで直す**（必須）
6. 元PDFを `pdf/<id>.pdf` にリネームする
7. `mcp__cowork__present_files` でJSONを提示し、「push.command をダブルクリック → y」と伝える

作業前に `README.md` を読み、既存の求人IDを確認すること。
`json/_sent/` にある既存JSONを1件読んで、文章の粒度・トーンを揃えてから書き始める。

**`json/` には今回の1件だけを置く。** 送信済みのJSONは push.command が
`json/_sent/` へ自動で移動するので、通常 `json/` は空になっている。
もし他社のJSONが残っていたら、`json/_sent/` へ退避してから書き出す
（残したまま送ると、その求人も一緒に上書きされる）。

## 絶対に守るルール

### 何のための文章か

この求人票は、**読んだ転職者が「応募したい」と思うためのもの。**
事実の一覧ではなく、その人の一歩を後押しする読み物として書く。

#### 書くこと

- **未経験から始められる根拠**（研修の中身、期間、同じ経歴の先輩の例）
- **入社後の道すじ**（1年目・3年目・その先に何ができるようになるか）
- **手に残るもの**（資格、専門知識、市場価値）
- **支える仕組み**（フォロー体制、相談相手、資格の費用負担）
- **数字**（定着率、未経験入社の割合、研修時間、有給取得率）

読み手は「自分にできるだろうか」と不安を抱えている。
**その不安に、こちらから答えを置いていく**書き方をする。

#### 書かないこと

不安をあおる要素は、**求人票には一切書かない。**

```
✗ 「繁忙期は残業が増えます」
✗ 「体力勝負の仕事です」
✗ 「離職率は高めです」
✗ 「厳しい環境で成長できます」
✗ 「向いていない方はすぐ辞めてしまいます」
✗ 「ノルマがあります」
✗ 「クレーム対応もあります」
```

**「向いていない方：〜」という記述は書かない。** 応募をためらわせるだけで、
条件の明示にはならない。伝えたいことがあるなら、歓迎条件として裏返して書く。

```
✗ requirements.mustNote に
   「向いていない方：黙々と1人で作業したい方」

○ requirements.want に
   「チームで進めることを楽しめる方」
```

打ち消して書くのは問題ない。むしろ不安を解くので歓迎する。

```
○ 「ノルマはありません」
○ 「肉体労働ではございません」
○ 「力仕事は求められません」
```

同じ内容でも、書き方で印象が変わる。事実を曲げずに前向きに書く。

| 避ける書き方 | こう書く |
|---|---|
| 覚えることが多く大変です | 3ヶ月の研修で、順を追って身につけられます |
| 転勤の可能性があります | 勤務地は希望を踏まえて決定します |
| 未経験には難しい仕事です | 未経験入社が8割。同じ立場から始めた先輩が揃っています |
| 残業が月20時間あります | 残業は月平均20時間。1日1時間ほどです |

#### 労働条件は事実のまま残す

**労働条件の明示は法律上必要。省いてはいけない。**
勤務地・勤務時間・残業時間・休日・給与・雇用形態は、原本の数字どおりに書く。

書き方を前向きにするのは構わないが、**数字を良く見せたり、
不利な条件を隠したりしてはいけない。** それは求人票の信頼を損なう。

#### 気になったことはチャットで伝える

原本を読んで気づいた懸念は、**求人票には書かず、報告のときにチャットで伝える。**
市川さんが求職者に口頭で補足するかどうかを判断する材料になる。

> 求人票には書いていませんが、気になった点を2つ。
> ・残業が月45時間までの記載があります（求人票には月平均20時間と記載）
> ・配属先が「全国」なので、転勤の範囲は広そうです

2〜3行で足りる。長々と書かなくてよい。**懸念が無ければ書かなくてよい。**

### 給与

**月給は必ず 20万〜30万円 の範囲で記載する。** 求人票の原本がこの範囲外でも調整する。

想定年収は月給から算術的に整合させる。

```
想定年収 = 月給 × 12 ＋ 賞与
```

- 原本の「年収例 510万円（月給42万円）」のような**月給30万超が前提の年収例は削除する**
- 原本の月給と年収が食い違っている場合は、月給を基準に年収を計算し直す
- 募集要項の給与欄と冒頭サマリーの数字は**必ず一致させる**
- 「※月給・年収は目安です。経験・スキル・配属先により異なります。」を注記に入れる
- **既存求人の給与を後から書き換えない。** 一度公開した求人の給与は、
  ユーザーから明示的に指示があるまで触らない

### 表記

#### 呼び名が2層になっている

**同じ求人が、見る人によって違う名前で表示される。** ここを理解していないと
文章が噛み合わなくなる。

| どこ | 表示 |
|---|---|
| `category`・一覧ページ・管理画面（社内） | **施工管理** |
| 求人票のページ（転職者が見る） | **建設事務** または **不動産事務** |

置き換えはサーバー側（`public/terms.php`）が表示のときに行う。
**JSONには原本どおり「施工管理」と書く。**
先に「建設事務」と書くと二重に置き換わって崩れる。

#### どちらの呼び名になるか

JSONに `displayTerm` を書いて指定する。**施工管理の求人では必ず書くこと。**

```json
{
  "id": "example-corp",
  "category": "施工管理",
  "displayTerm": "construction",
  ...
}
```

| 値 | 転職者への表示 | 使う求人 |
|---|---|---|
| `construction` | 建設事務 | 建築・建設・プラント・土木・内装・設備 |
| `realestate` | 不動産事務 | 不動産・賃貸・売買・仲介・物件管理 |

書き忘れても本文の語から自動で判定されるが、**明示するほうが確実**。
`category` が「施工管理」でない求人には書かなくてよい。

#### 置き換えた後に読んで確かめる

これが一番大事。**「施工管理」を「建設事務」に入れ替えても自然に読める文章を書く。**
入れ替えると壊れる書き方が実際にあった。

```
✗ 「施工管理技士は国家資格です」
    → 置き換え表で個別に処理しているが、似た新しい言い方を作ると壊れる

✗ 「事務ではなく、施工管理としてやっていきたい方へ」
    → 「事務ではなく、建設事務として」になり矛盾する

✗ 「体力に自信のある方、現場を走り回りたい方」
    → 事務という呼び名と印象が食い違う
```

書くときのコツ。

- **「現場監督」「職人」「体力」「汗をかく」といった語は使わない。**
  事務という呼び名と印象がぶつかる
- 仕事内容は「図面の確認」「工程の管理」「写真の整理」「関係者との調整」のように、
  **デスクワークとして成立する言い方**で書く
- 「現場に足を運ぶ」ことは書いてよい。ただし主役は管理・調整であるように書く
- 資格の話は「建築系の国家資格」という言い方で書けば置き換えに巻き込まれない

JSONを書き終えたら、**頭の中で「施工管理」を「建設事務」に置き換えて読み直す。**
おかしな箇所があれば直す。置き換え表に無い新しい言い方
（例「施工管理エンジニア」）を作った場合は、そのまま求人票に出てしまうので、
報告で一言添えて `terms.php` への追加が必要かユーザーに確認する。

- **「無期雇用派遣」「登録型派遣」「派遣社員」「派遣先」「有料職業紹介」は使わない。**
  雇用形態は「正社員」、勤務先は「就業先」「配属先企業」、事業は「人材派遣／人材紹介」と書く
- ただし「当社の正社員として入社し、取引先企業で就業いただく」という**枠組みは残す**。
  実際の勤務地・指揮命令系統は労働条件の明示として必要
- **求人提供元（紹介事業者）の情報は一切載せない。**
  PDF末尾の事業者名・許可番号・苦情窓口・手数料・違約金・返戻金はすべて除外する
- 掲載企業自身の会社情報・実績・クライアント名は載せてよい

### 年収の推移（salarySteps）

転職者が一番知りたい「この先どうなるか」を見せる項目。
**ただし、根拠が無ければ書かない。** 推測で埋めるより空欄のほうがよい。

#### 想定年収レンジの意味を間違えないこと

これを取り違えた求人票が過去に量産されたので、**必ず読むこと。**

`stats` の想定年収（例「約350万〜420万円」）は、**初年度に提示される金額の幅**である。

- レンジの**上限は到達点ではない。** 「10年経っても420万円まで」という意味ではない
- 実際に提示されるのは、**レンジの真ん中より少し上**が目安

したがって salarySteps は、こう組む。

| 段 | 置く数字 |
|---|---|
| 1年目 | レンジの**中央より少し上**（下限ではない） |
| 2段目以降 | **レンジ上限で止めない。** Webで調べた実際の水準にもとづく |

やってはいけない組み方の例。

```
想定年収 約350万〜420万円 のとき

✗ 1年目 350万 → 3年目 420万 → 5年目 420万
    下限を1年目に、上限を天井にしてしまっている

○ 1年目 390万 → 3年目 450万 → 5年目 520万 → 10年目 650万
    初年度は中央より少し上。以降は調査にもとづき上限を超える
```

#### 調べ方

次の順に当たる。**上のほうが信頼できる。**

1. **有価証券報告書**の平均年間給与（上場企業のみ）
2. **厚労省 job tag** の職種別・経験年数別（[shigoto.mhlw.go.jp](https://shigoto.mhlw.go.jp/)）
   … 会社固有ではないが、公的統計なので土台に使える
3. **公式採用サイト**のモデル年収、資格手当・昇給制度の金額
4. **doda / マイナビ転職**の企業ページのモデル年収
5. **OpenWork / エン ライトハウス / Yahoo!しごとカタログ**の年齢別・年次別
   … 必ず**回答者数（サンプル数）**を見る。数十人未満の数字は弱い

#### 落とし穴

- **持株会社の平均年収を、事業会社の数字として使わないこと。**
  従業員が数十名の管理部門だけの数字で、現場社員の給与とは無関係。
  過去に実際に紛れ込みかけた例：オープンアップグループ 750万（123名）、
  ウィルグループ 676万（98名）、ナレルグループ 990万（24名）
- **求人票のモデル年収は、口コミ実績の1.3〜2.4倍になりがち。**
  両方を見て、**実績側に寄せる**
- 口コミサイトの平均年収は集計期間が10年ぶんに及ぶことがある。年度を確認する
- Indeed の「平均月給」は求人票の機械集計による推定値。社員の実績ではない
- 同じ会社でも掲載年でモデル年収が大きく違うことがある。**新しいものを使う**

#### 分からないときは空欄にする

会社固有のデータが見つからず、職種一般の水準しか分からない場合は、
**`salarySteps` を書かない**（キーごと省略する）。セクションは自動的に出なくなる。

中途半端に埋めるより、無いほうがよい。**報告のときに
「年収の推移は根拠が見つからなかったので入れていません」と伝えること。**

#### 書き方

- `stage` は「入社1年目」「3年目」「5年目」のように**時期**
- `salary` は**その時点の想定年収**。金額以外（「半期に一度」など）を入れてもよいが、
  長い文章は避ける（丸ごと表示され、文字が小さくなる）
- `note` に、上がる理由（資格取得・役割の変化）を一言添える
- **2段目以降は月給20〜30万円の縛りを受けない。** 将来の年収なので対象外
- `note`（全体）に「モデルケースであり保証ではない」旨を必ず入れる

### 密度

**全セクションを埋める。** 目安は下記。素材が足りなければWebで補う。

| セクション | 目安 |
|---|---|
| numbers（訴求数字） | 4件。**label は必須**（丸の中に出る「何の数字か」。6文字前後） |
| about.points | 4件 |
| about.flow | 4〜5ステップ |
| duties.list | 5〜6件 |
| duties.items | 3件（1年目／3年目／その先の時系列が書きやすい） |
| salarySteps | 3〜4段階。**根拠が無ければ書かない**（唯一の任意項目） |
| showcase | 必須。実績・配属先・プロジェクト例 |
| schedule.items | 7件（休憩は body を空に） |
| appeals.items | 6件 |
| training.items | 6件 |
| outline | 10〜12件 |
| flow.steps | 3〜4件 |
| vision | 必須 |

**1日のスケジュールは原本に無くても必ず作る。** 求人票の勤務時間・残業実績と
職種の一般的な流れから組む。事務職なら 9:00〜18:00、施工管理なら 8:00〜9:00 始業が基本。

## 点検スクリプト（書き出したら必ず実行する）

```bash
python3 tools/check-json.py             # json/ の全件
python3 tools/check-json.py json/x.json # 1件だけ
```

給与の算術・禁止語・必須キー・空セクション・各セクションの件数を機械的に確認する。
**✗ がひとつでも残っている状態でユーザーに報告しない。**
出力の最後が「すべて問題ありません」になってから提示する。

## 複数人で使っている場合（重要）

このフォルダは**複数のキャリアアドバイザーが同時に使っている**。
サーバーは1つなので、他の人が追加した求人も同じ一覧に並ぶ。
自分の `json/_sent/` には**自分が送ったぶんしか入っていない**ので、
それだけを見て判断すると、他の人が登録済みの会社を二重に登録してしまう。

### 作り始める前に、サーバーの現況を必ず確認する

`json/_server.json` を読む。`push.command` を実行するたびに更新される、
**全員ぶんの登録状況**が入っている。

```json
{ "ok": true, "fetchedAt": "2026-08-14 10:00",
  "categories": ["事務", "施工管理"],
  "jobs": [ { "id": "yell", "company": "株式会社エール",
              "category": "施工管理", "status": "published",
              "data": { "…求人票の中身がまるごと入る…" } } ] }
```

`data` には、**いまサーバーにある本文**が入っている（成約フィーを除く）。
管理画面で直された文章もここに反映されている。既存の求人を部分更新するときは、
**必ず `data` を読んでから**書くこと。読まずに配列項目（`numbers` など）を
送ると、いまの中身がまるごと置き換わる。

`data` が無いときは、サーバーの `import.php` が古い。市川さんに
「`public/api/import.php` を上げ直してください」と伝える。

`fetchedAt` が古い（数日前など）ときは、`push.command` をダブルクリックして
`N` で抜けてもらえば更新される。**サーバーへ直接読みに行くことはできない**
（Cowork からこのドメインは開けない）。

取れなければ `json/_server.json` の内容で進めてよい。両方無ければ
`json/_sent/` を見るが、その場合は**報告で「他の人の登録状況は確認できていません」と伝える**。

### 確認すること

1. **同じ会社が既に無いか**（`company` を照合する。「株式会社」の有無や
   スペースの違いは無視して比べる）
   - あれば、**同じ `id` を使う**。中身が新しい求人票で置き換わる
   - 別の求人として並べたいなら、`id` の末尾を変えて区別できる名前にする
     （例：`yell-office` / `yell-construction`）。この場合は報告で必ず確認を取る
2. **カテゴリの表記**は `categories` に合わせる。ここに無い名前を使うと
   一覧ページにセクションが増える
3. **IDが既にある**場合は「更新」になる。管理画面で他の人が直した文章は
   元に戻るので、報告でその旨を伝える

`push.command` も送信前に同じ検査をして、`同じ会社が、別のIDで既に登録されています`
と警告を出す。ただし**そこで気づくのでは遅い**（JSONを作り直すことになる）ので、
作り始める前に確認する。

## 職種カテゴリ

`category` は一覧ページのセクション単位。**新しい名前を入れれば自動でセクションが増える。**
`admin/config.php` の `CATEGORY_ORDER` は表示順を決めるだけで、そこに無いカテゴリでも登録できる
（並び順は末尾になる）。

既存のカテゴリは `json/_sent/*.json` を見れば分かる。
**必ず既存の表記に合わせる。** 「営業」と「営業職」を混ぜるとセクションが2つに割れる。
push.command は新カテゴリを `★新` として警告し、似た名前があれば知らせるので、
`y` の前に必ず確認するようユーザーに伝える。

順番を指定したい場合だけ `public/admin/config.php` の `CATEGORY_ORDER` に1行足す。

## Webリサーチで補強する項目

`WebSearch` で以下を調べる。会社名＋職種＋「研修 未経験 評判」で1〜2回検索すれば足りる。

- 研修制度の具体名・期間・時間数
- 未経験入社率、定着率、資格合格率、直接雇用・転籍の実績数
- 施工実績・配属先企業などの固有名詞
- グループ会社・上場区分

**求人票に書かれた事実と矛盾しない範囲で使う。** 給与や労働条件の数字は
Webの情報で上書きしない。求人票の主張を裏づける方向にだけ使う。

口コミサイトのネガティブな指摘は求人票に載せないが、
面談で聞かれる可能性があるので**報告の中でユーザーに共有する**。

## ID とファイル名

`id` は会社名ベースの英語 kebab-case。既存と重複しないこと。

```
株式会社ワット・コンサルティング   → wat-consulting
株式会社ウィルオブ・コンストラクション → willof-construction
パーソルエクセルHRパートナーズ      → persol-excel-hr-partners
```

- JSON … `json/<id>.json`
- PDF  … `pdf/<id>.pdf`（元PDFをリネーム）

`status` フィールドは**書かない**。push.command 側で公開状態を決める。

## JSONスキーマ

すべて任意。空にした項目はページに表示されない。

`displayTerm` はページには出ない指定用の項目。
`category` が「施工管理」のときだけ書く（`construction` か `realestate`）。

`regions` は一覧ページの絞り込みに使う社内用の項目。求人票ページには出ない。
**すべての求人に必ず書く。** 勤務地から判断する。

| 勤務地 | regions |
|---|---|
| 東京・神奈川・埼玉・千葉・茨城・栃木・群馬・首都圏 | `["関東"]` |
| 大阪・京都・兵庫・奈良・滋賀・和歌山 | `["関西"]` |
| 両方に拠点がある | `["関東", "関西"]` |
| **全国** | `["関東", "関西"]` |

勤務地が東海や九州だけの場合は、その地名をそのまま入れてよい
（例 `["東海"]`）。一覧ページの絞り込みボタンは登録されている拠点から
自動で作られるので、ボタンが増えるだけで壊れない。

なお **`agentNotes`（エージェント確認事項）は書かない。**
管理画面で市川さんが入力する項目で、取り込みでは上書きされない。

## 書き出したあとの案内

JSONを提示して、こう伝える。

> **反映のしかた**
>
> フォルダ直下の `push.command` をダブルクリック → 内容を確認 → `y` を入力
>
> 新しい求人は**限定公開**で入ります。公開に切り替えるのは管理者（市川さん）です。
> 送信が終わったら市川さんに連絡してください。かつては管理画面（`/admin/`）で
> 「公開する」を押すと、`https://（ドメイン）/（設置場所）/job/<id>/` が有効になります。
> 送信できたJSONは `json/_sent/` に自動で移動します。

### 公開状態の仕組み（間違えやすいので必ず把握する）

| 対象 | 挙動 |
|---|---|
| **新規**の求人 | 限定公開で入る（`PUBLISH="false"` が既定） |

### 公開状態は3種類ある

| 値（JSON） | 画面の表示 | 一覧に出るか | ページが開くか |
|---|---|---|---|
| `published` | 公開中 | 全員に出る | 開く |
| `draft` | **限定公開** | 管理者にだけ出る | 開く（URLを知っていれば誰でも） |
| `private` | 非公開 | 管理者にだけ出る | 開かない（管理者だけ確認できる） |

`draft` という値は昔から使っているので変えていない。**画面に出る言葉だけ
「限定公開」**になっている。ユーザーが「下書き」と言ったら限定公開のこと。

JSONに `status` は書かない。サーバー側が管理する。
| **既存**の求人 | 内容だけ差し替わり、**公開状態はサーバー側のまま維持される** |

`api/import.php` は既存の求人に `status` を書き込まない。
そのため**すでに公開中の求人が取り込みで限定公開に戻ることはない。**

`push.command` の `FORCE="true"` だけがこの保護を外す。
公開中の求人を一括で限定公開に戻したいとき以外、**絶対に true にしない。**
ユーザーから「全部下書き（限定公開）になってしまった」と言われたら、まず
`json/` に他社のJSONが残っていなかったか、`FORCE` が true になっていないかを確認する。

Cowork から本番サーバーへPOSTすることはできない（実行環境で外部への送信が
許可されていない）。送信はユーザーのMacからになる。この点は聞かれたら説明する。

### 反映後の疎通確認

`mcp__workspace__web_fetch` でGETは可能。

```
https://（ドメイン）/（設置場所）/api/import.php?ping=1
→ {"ok":true,"service":"job-import","ready":true}
```

## 報告の作法

- **給与を調整した場合は、原本の数字と掲載する数字を対比表で必ず報告する**
- Webから補強した内容を、どこに反映したか箇条書きで示す
- **原本やWebで気づいた懸念点は、求人票には載せず、報告の中で簡潔に伝える**
  （残業時間の上限、転勤の範囲、離職に関する口コミ、賞与の実態など。
  2〜3行で足りる。無ければ書かなくてよい）
- 施工管理の求人では、**転職者に見える呼び名（建設事務／不動産事務）を報告に書く**
- **`tools/check-json.py` が「すべて問題ありません」を返したことを確認してから報告する**
- 新しい職種カテゴリになる場合は、その旨と `CATEGORY_ORDER` の話を添える

### 報告のテンプレート

```
N社分のJSONを作りました。

| | A社 | B社 |
|---|---|---|
| 月給 | 22万〜28万円 | 25万〜30万円 |
| 想定年収 | 約308万〜392万円 | 約350万〜420万円 |
| 転職者への表示 | 建設事務 | （施工管理以外なので該当なし） |
| 訴求 | … | … |

（原本と変えた点、Webから補った点を簡潔に）

**求人票には書いていない気になった点**
・（あれば2〜3行。無ければこの見出しごと省く）

**次の操作**
1. push.command をダブルクリック → y
2. 管理画面で内容を確認 → 公開状態を「公開中」に
```
